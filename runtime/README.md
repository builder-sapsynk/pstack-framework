# External-agent process boundary

Invoke `python runtime/cli.py run --request job.json [--project /absolute/project]` in a retained terminal session. Request fields: `provider` (`claude`, `grok`, `codex`), opaque `model`, optional independent `effort`, `mode` (`read-only`, `isolated-write`), absolute `project`, `cwd`, and either an absolute `prompt_file` or private inline `brief`. Prompt files are read as UTF-8 with a 1 MiB bound; when both are supplied, the file is authoritative. An optional positive finite `timeout` is the sole task deadline, including preflights. No fallback or automatic task timeout exists.

`doctor --project PROJECT --json` reports installation and authentication preflight separately from authenticated execution. `status --project PROJECT --job ID`, `cancel --project PROJECT --job ID`, and `checkpoint --project PROJECT --job ID FILE` address durable jobs. Interrupted runner receipts remain preserved; status reports lost liveness using Linux process start identity. Checkpoint recovery creates a new attempt. For completed direct Grok sessions, explicit `resume_job` creates a new receipt while retaining validated prior context; never blindly relaunch a dead job.

`CLAUDE_BINARY`, `GROK_BINARY`, `CODEX_BINARY` select installed executable paths. Environment binary settings override project/default executable settings; request `executable` overrides both. Optional `providers.PROVIDER.executable` and `.dialect` are loaded from plugin `config/defaults.json`, then project `.pstack/config.json`; explicit request wins. Model and effort are always assigned by the coordinator. Credentials never belong in configuration or requests.

The Grok response-only lane uses the exact named dialect `{"id":"grok-build-1","confinement":"response-only"}` with portable `mode: "read-only"`. This profile returns an output artifact without model tools. It refuses `isolated-write`, command approvals, unknown confinement values, and additional dialect fields. The coordinator supplies approved file contents in the brief, inspects the response, and applies artifact changes and tests locally. The native process has no verified filesystem or credential isolation. Native bwrap profiles failed on this cloud host, and Landlock was unavailable. Receipts report `filesystemSandbox: "off"` and `filesystemIsolation: "unavailable"`.

The response-only named profile copies the complete brief and bounded worker instruction into the job's private `brief.txt` and passes `--prompt-file`. Prompt text stays out of argv and stdin. The profile pins the requested model, optional `--reasoning-effort`, `--cwd`, `--output-format streaming-messages-json`, `--sandbox off`, and `--permission-mode dontAsk`. It disables subagents and web search. Native `--tools read_file --disallowed-tools read_file,search_tool,use_tool` produces an empty tool list in the observed CLI. An empty `--tools` argument enables defaults and is never used. All providers receive the instruction against framework rerouting and recursive delegation.

Before model dispatch, help must confirm the required flags. `grok models` must report the observed grok.com login line and the exact requested model in its available catalog. `grok inspect --json` must report no hooks, MCP servers, project instructions, or plugins. Discovered agents must be built-ins. Skills must be built-ins or bundled skills whose canonical paths stay under `GROK_HOME/bundled/skills`. The environment disables memory, subagents, tool search, file writing, web fetch, LSP tools, and Cursor and Claude compatibility scanners. It disables automatic updates and preserves inherited proxy, TLS trust, Grok home, and provider authentication settings. Server-bundled skills and slash commands can still appear in native init metadata and remain recorded observations. No claim of complete native skill or rule suppression follows from those controls.

The named parser requires an initial native session and exact served model, matching session IDs throughout, exact assistant models, no advertised tools or MCP, and the expected cwd and permission mode. A nonempty terminal result must have `subtype: "success"`, `is_error: false`, and `stop_reason: "end_turn"`. Tool blocks, server tool usage, errors, truncation, unknown events, and events after completion fail the job. Native thinking blocks stay in private raw evidence and never become the response artifact. `modelUsage`, including `grok-4.7-build`, remains billing metadata separate from served-model identity. Effort is pinned argv evidence, not proof of the model's internal effort. `doctor` separates version, help, authenticated catalog, and discovery checks from live execution proof.

The legacy explicit Grok dialect remains supported for reviewed fixtures and other versions. It requires `auth_argv`, `run_argv`, and `required_flags` arrays. Run argv supports `{model}`, `{effort}`, `{mode}`, and `{cwd}` placeholders and retains stdin transport. It does not acquire the named profile's native schema or capability claims. Permission bypass arguments, including `--always-approve`, `--yolo`, and bypass permission modes, are prohibited.

Claude 2.1.288 help confirms the restricted profile. Read-only Claude has Read/Grep/Glob with no Bash, write or agent tools; restricted mode confines file tools. Isolated writers receive Edit/Write in a separate Git worktree belonging to the project common directory, at its root, or explicit initially empty scratch outside the main project. An OS file lock reserves each writer directory and releases on process death. Explicit `allowed_commands` adds scoped Claude Bash command-prefix approvals for verification; without those approvals Bash stays disabled. Read-only workers never gain Bash. Codex uses native sandbox flags and disables plugins, multi_agent, hooks, and memories in external workers. Execution fails closed unless the CLI features list confirms all four controls. The submitted worker brief explicitly prohibits framework rerouting and recursive delegation; its digest covers the complete submitted prompt. Host sandbox and CLI controls remain authoritative; directory ownership checks do not create OS isolation. Environment filtering removes other provider credentials but preserves git credentials (workers push their own branches), proxy/trust settings and assigned provider keys. Provider on-disk credentials remain accessible; this is not a credential sandbox.

Receipts, private prompt, response and provider events live in unique mode-0700 `.pstack/runs/ID` directories, with mode-0600 files. CLI stdout immediately emits a flushed `job.started` JSON event containing the durable job ID before execution, followed by the final receipt JSON. Python callers can supply `on_start`; default function calls stay quiet. Receipts include a SHA-256 prompt digest, sanitized effective request, host/source pin when provided, subprocess transport, pinned argv, reported model evidence, metrics when present, elapsed time, and terminal status. Private provider stdout, stderr, and raw structured events are preserved for nonzero exits, malformed responses, and model mismatches as well as success; receipt paths identify this evidence without printing its content. Nonzero exit, malformed output, empty response, absent successful terminal event, missing provider model report (except Codex pinned-argv evidence), model mismatch, timeout and cancellation are failures rather than reviewer votes. Keep `.pstack/runs` ignored and never commit evidence containing prompts.

Tests use explicit fake CLI fixtures. Passing them does not establish live provider access. Genuine Grok Build 1.0.46 native read/edit/command drives, owned parallel writers, chained follow-up sessions and local cancellation were captured separately. Their shared managed-host boundary does not establish separate-VM, credential or native Codex API parity. A live external Codex read-only file-read probe has succeeded after device authentication and approved host execution. Claude live responses remain unverified. Quota, account concurrency, and replacement-VM credential persistence remain unknown.

Authentication transport preserves OPENAI_API_KEY, CODEX_API_KEY and CODEX_ACCESS_TOKEN for Codex workers. Login preflight is only cached credential availability; receipts set authVerified only after successful execution. For headless ChatGPT login use the official `codex login --device-auth` flow and wait for the CLI completion message before dispatching. Parent cloud-agent authentication does not establish standalone CLI authentication. See https://developers.openai.com/codex/auth.

## Direct native Grok tools

The default Grok profile is `{"id":"grok-build-native-1","confinement":"managed-host"}`. Read [the managed-host adapter](../adapters/grok-native.md) before dispatch. Requests require a truthful supported `host_boundary` declaration; the runtime probes a denied outside-write boundary and refuses an unconfined launch. Native file tools and exact literal `allowed_commands` execute directly through the official CLI, with no MCP or command bridge. The coordinator launches through the actual managed host execution tool. Explicit inventory filters, matched native tool/results, model/session/terminal checks and per-worktree writer locks remain required.

`{"id":"grok-build-native-task-1","confinement":"managed-host"}` is an opt-in full native lane, not a silent upgrade of the restricted profile. The same profile id governs validation, environment, private home config, argv, the worker header, inspect, the parser, resume, and doctor. It discovers the trusted CLI's init tool list instead of pinning the restricted inventory. It enables autonomous terminal commands, web fetch/search, file creation/edit for isolated writers, and native child agents when init actually lists them. It still refuses always-approve, yolo, and bypassPermissions, and it still refuses configured MCP servers, third-party hooks, and project agents. Native tool search and dispatch remain available. The worker header reserves role resolution and spawning for the coordinator, even when native child tools are discovered. Positive web-search usage is accepted on this lane after normalize; response-only and restricted native parsing stay strict. Matched recoverable tool errors and text, JSON, or list tool results are accepted. Session, model, unique tool-call identity, and terminal ordering stay strict. Canonical reads may leave the cwd when they remain inside declared writable roots. Recorded direct file calls are scored against the worktree after execution; terminal, child and deferred dispatch paths are not confined by that scoring. Configured capabilities that init does not advertise stay unverified. An init observation is not artifact verification. User-authorized limits such as no merge, push, or deploy are instructions. A trusted terminal can reach further unless the host sandbox enforces that limit. Do not copy project or framework sources for the worker.

Optional `resume_job` addresses a completed owned native job, preserves validated session ownership across successive follow-ups and exclusively locks the reused session. Optional absolute `workflow` instruments private lifecycle stages and imports receipt usage once per job. Final receipt `summaryLines` contains two deterministic observed metrics lines without changing stdout into a prose protocol. Native coordinator events require host-side instrumentation. Current context occupancy stays unknown when unreported.

Cancellation retains descendant PID/start identities through TERM/KILL escalation and bounded pipe draining, including detached command descendants. Partial native stdout/stderr survives timeout or cancellation. A nonexecuting orphan zombie can remain until the host reaps it; this is distinct from a running process. Remote model API cancellation is unverified.

The broad task lane is not activated for this shared cloud host. Its approval reviewer rejected unrestricted launches despite explicit owner authorization. Cloud internet access is already unrestricted. Official [Agent approvals and security](https://developers.openai.com/codex/agent-approvals-security) distinguishes user-reviewed approvals from automatic review and managed constraints. Changing a brief or a local config file cannot override the active host policy. A separate isolated native-tool proof succeeded, but no container or ACP adapter was adopted as the project default. Preserve the direct CLI preference and require a permitted host launch before promotion.

## Worker resources

Both runners emit a canonical `resources.json` manifest and include it in the submitted prompt. The managed receipt lists this artifact, and its prompt digest covers the complete manifest and brief. Native `pstack-worker` briefs require the same manifest from the coordinator.

`runtime/worker_resources.py` resolves the framework from the running package. A framework source checkout uses its generated `plugins/sapsynk-pstack` package. The manifest records that package's `framework.json`, the canonical project root, and the project `.pstack/framework.lock.json` when present. Version, source digest, and upstream revision must match the project pin before launch.

`required_paths` contains absolute paths to the portable contract, host mapping, configuration, sapsynk-pstack entry, and Poteto Mode. It also includes project AGENTS policy, `.agents/skills/sapsynk-project/SKILL.md`, and `.agents/skills/verify-*/SKILL.md` when present. Absolute skill, playbook, and persona paths named in the brief remain required. The manifest lists exact available playbook paths. The coordinator names the applicable principles and leaves in the brief. Workers read required files in full, apply the matched playbook, and preserve bootstrap and verification duties. Router dispatch, role resolution, task rerouting, and spawning belong to the coordinator.

Optional dyl, learning, and teamkit resources are required only when the project locks those plugins or the brief names their paths. For `.pstack/plugins.lock.json`, named leaf paths identify each canonical plugin root first. Otherwise resolution checks the pinned marketplace checkout under `PSTACK_HOME/plugins/<source_revision>/plugins/<name>`, then the exact locked version in the Codex and Claude plugin caches. Every file digest in the plugin lock must match. Ambiguous named roots, missing files, unreadable files, and lock mismatches prevent provider launch. No provider CLI discovery or source copying is used to resolve resources. A framework-only project requires no optional plugins.

The manifest proves host readability and lock agreement. It does not qualify provider file tools. A worker whose actual tools cannot read a required path reports the integration unavailable and stops. Managed restrictions stay in force, including response-only Grok's lack of file tools and restricted Claude's command limits. Bootstrap or verification commands blocked by those restrictions remain unavailable. Learning promotion and hook activation are never automatic.

## Local worker runner

`pstack_run.py` is the worker path on an owner-controlled host. Projects call it through `scripts/pstack-run`, which resolves the pinned package first. It is separate from the request-file runtime above and does not use its dialects or host-boundary declaration.

```sh
scripts/pstack-run run <codex|grok|claude> <task-id> <brief-file> [--role "<role>"] [--mode write|read]
scripts/pstack-run resume <task-id> <brief-file>
scripts/pstack-run status [<task-id>] [--full]
scripts/pstack-run diff <task-id> [--patch]
scripts/pstack-run kill <task-id>
scripts/pstack-run clean <task-id> [--force]
scripts/pstack-run doctor
```

`run` blocks until the worker is terminal. Start each worker as its own background task; stdout carries one `pstack.started` line and one final receipt line. A write task commits on its own branch in the worktree `../.pstack-worktrees/<project>/<task-id>` on branch `pstack/<task-id>`, based on `--base` or HEAD. A read task runs in the project unless `--worktree` or `--cwd` says otherwise. `PSTACK_WORKTREE_ROOT` moves the worktree directory. A task id is reused only through `resume` or an explicit `run --force`.

The run directory `.pstack/runs/<task-id>/` holds `brief.md`, the submitted `prompt.txt`, `resources.json`, `events.jsonl`, `stderr.log`, `last-message.txt` and `status.json`. The event log is the provider's own JSON lines plus `pstack.*` lifecycle events; non-JSON output is wrapped as `pstack.raw`. `status.json` records `state`, `session_id`, `pid`, `exit_code`, `cost_usd`, `usage`, a summary capped at 2000 characters with `summary_truncated`, per-attempt `attempts` history with `totals` across resumes, the diffstat against the task base, model, effort, limits and the exact argv.

| Provider | Write mode | Read mode | Session |
| --- | --- | --- | --- |
| codex | `exec --json --dangerously-bypass-approvals-and-sandbox` | same flags | `thread.started` id, `exec resume` |
| grok | `--output-format streaming-json --permission-mode bypassPermissions --always-approve` | same flags | assigned `--session-id`, `--resume` |
| claude | `-p --output-format stream-json --dangerously-skip-permissions` | same flags | assigned `--session-id`, `--resume` |

Every worker runs with full autonomy: no OS sandbox, no approval prompts, every tool, full network. The runner is meant for a dedicated machine the owner controls; isolation is the task worktree. Read mode is a contract in the brief, not a tool restriction. `--permission-mode` can narrow grok or claude for one run. The brief goes through a file or stdin, never argv. The worker inherits the host environment, GitHub login included; only other model vendors' API keys are withheld.

The hard guardrails are in the worker header: commit only on the task branch, push only the task branch (never main), never merge, force-push, delete a remote branch, deploy, send customer-facing messages, or print or copy credentials. Per-run Git hooks in `.pstack/runs/<task-id>/hooks` back the first three: `pre-commit` refuses a commit on any other branch, `pre-push` refuses main, deletions and non-fast-forward pushes. The project's own hooks still run. The hooks are a tripwire for a cooperating worker, not a security boundary.

Three deadlines apply: `--startup-timeout` (120 s to the first event), `--idle-timeout` (900 s between events) and `--timeout` (3600 s total); 0 disables one. A breach stops the worker's process group and yields `startup_timeout`, `stalled` or `timeout` with exit code 124. `kill` gives `killed` and 130. A status whose runner died without a receipt reads as `lost`. Success requires exit 0, the provider's successful terminal event and a nonempty final message.

`--role` reads model and effort from that role in `.pstack/config.json` and fails when the role has no binding for the chosen provider. Without it, `host_bindings.claude-code.workers.<provider>` applies, then the CLI default.

Fixture tests cover lifecycle, watchdogs, kill, resume, flag construction and the guard hooks. Live Codex 0.160.0 and Grok Build 1.0.46 workers ran in parallel with these flags on a Debian 13 host; each reached the network, ran shell commands and committed on its task branch unattended. The external Claude profile was not rerun live with the bypass flag.
